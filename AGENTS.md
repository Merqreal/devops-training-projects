# Instructions for assignment authors

- Inspect status and existing files before editing. Preserve unrelated work. Use a dedicated feature branch. Do not push, publish, or enable Pages without explicit user authorization.
- This repository contains a training portal, not learner implementations. Never add a complete Terraform/Helm solution to learner content.
- Use Zensical and the existing design/navigation. Keep dependencies minimal and pinned in requirements-docs.txt. Never replace the site with another framework.
- For every new project use templates/project.md and templates/project.json. Supply all 17 sections: ID/title; difficulty/duration; business problem; learning objectives; prerequisites; architecture; mandatory stack; functional requirements; infrastructure requirements; security requirements; milestones/deliverables; acceptance criteria; verification; submission structure; constraints/non-goals; optional goals; reviewer guidance.
- Read docs/platform/architecture.md before architectural changes. Follow its domain, identity, metadata, lifecycle, navigation, versioning and deprecation conventions; do not implement proposed roadmap features unless requested.
- Allocate permanent DEVOPS-NNN IDs independently of paths. Never reuse or renumber retired IDs. Store definitions in projects/DEVOPS-NNN/project.json, public content in docs/projects/<primary-domain>/<slug>/ and notes in reviewers/DEVOPS-NNN.md. Group by technical domain, never by difficulty. Use domains/tags for cross-domain projects.
- Validate every definition against platform/schemas/project.schema.json using scripts/project_metadata.py. Keep structured difficulty, effort, prerequisites, lifecycle, technologies, domains, tags, ordered pages and assignment version. Keep templates schema-valid. Update schema_version with an explicit migration for incompatible contract changes.
- Generate docs/projects/index.md with scripts/project_metadata.py --write. Match zensical.toml Projects navigation to project_metadata.py --navigation; validation enforces exact metadata-derived domain groups and pages. Use relative links and tagged code fences.
- Reference permanent project IDs from future learning paths; never duplicate assignments. Use semantic assignment versions and Git history; retain deprecated/archived definitions with reason/replacement metadata. Preserve published URLs with a notice or redirect when moving content. Draft pages are not private. Keep the site functional without a backend database.
- Separate mandatory work from optional enhancements. Define outcome-based acceptance and real evidence requirements. Keep learner content solution-neutral.
- Pin tools/charts/providers/images, inspect versioned upstream configuration, cite sources and record verification date. Never claim deployment, tests, or compatibility were demonstrated if only documentation was inspected.
- Put detailed reviewer criteria, failure modes, expected explanations and reference strategy in reviewers/DEVOPS-NNN.md, never in docs/. Include the REVIEWER_ONLY_DO_NOT_PUBLISH marker in each reviewer file. Use templates/reviewer.md.
- Never copy reviewer files with includes, symlinks, generated pages, assets, or search entries. Reviewer files remain visible in Git: they are excluded from publication, not access-controlled.
- Do not commit secrets, state, saved plans or generated site files. Examples must not contain real credentials. Explain residual secret exposure when relevant.
- Before handover run .venv/bin/python -m unittest discover -s tests, .venv/bin/python scripts/project_metadata.py, .venv/bin/zensical build --strict and .venv/bin/python scripts/validate_docs.py. Inspect generated HTML/search assets for reviewer material, review git diff and disclose validation limitations. Do not deploy the learner's infrastructure unless explicitly requested.
- Public GitHub Pages publication was explicitly authorized in this session. Deploy automatically only on pushes to main, with optional manual dispatch restricted to main. Keep validation on pull requests. Use official Pages actions, contents: read, scoped pages permissions, id-token: write for deployment, the github-pages environment, and serialized deployment concurrency. Never bypass branch protection or publish reviewer content.
